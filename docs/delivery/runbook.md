# دليل تشغيل خطة ترجمان

> **«متى وكيف».** «ماذا ولماذا» في [مواصفة المنتج](../product-spec.md)، وتنظيم الموجات وملكية الملفات في [الموجات](waves.md). هذا الملف مصدر نصوص الأدوار وصيغ التقارير التي تنسخها اللوحة في البرومبت الكامل، فأي تعديل فيه يظهر في البرومبتات بعد `npm run plan:sync`.

## الفكرة في ثلاثة أسطر

1. تفتح [اللوحة](../../dashboard/index.html) فتعرف المنجز والجاري والمتعطل والخطوة التالية، وتنسخ أمر المرحلة إلى **جلسة مستقلة** تختار نموذجها.
2. الجلسة تنفّذ نطاق مرحلتها في **worktree وفرع خاصين بها**، وتلتزم وتدفع فرعها بعد كل مهمة، وتفحصه، وتسلّمه، وتتوقف. لا تنتقل إلى مرحلة أخرى.
3. بعد تسليم مراحل الموجة تفتح **جلسة منسّق** في النسخة الرئيسية وتنسخ أمر الموجة، فيكتشف الفروع والتقارير بنفسه، ويدمج بالترتيب، ويفحص التكامل، ويحدّث الحالة، ثم يدفع `main` ووسم الموجة التالية. لا تنقل تقارير ولا تكتب أسماء فروع ولا أوامر Git.

## المفاهيم

| المفهوم | المعنى |
| --- | --- |
| **المرحلة** `P1`…`P9` | وحدة عمل لجلسة واحدة، بنتيجة قابلة للتسليم والفحص، وملكية ملفات محددة. |
| **الموجة** `W1`…`W5` | مراحل تُدمج معًا. المراحل داخل موجة مستقلة فعلًا، فتعمل بالتوازي. |
| **وسم الأساس** `tj-W3/base` | يضعه المنسّق على `main` بعد تحقق الموجة السابقة؛ وجوده هو الدليل الوحيد على أن الموجة مفتوحة. |
| **فرع المرحلة** `tj/P3-export` | فرع محلي في worktree مستقل `.claude/worktrees/tj-P3`. |
| **فرع التكامل** `tj-int/W3` | يدمج فيه المنسّق فروع الموجة ويشغّل البوابة؛ ولا يتقدم `main` إلا بعد نجاحها. |
| **البوابة** `G1` | قرار يُحسم بعد موجة: تُفتح تلقائيًا بنتيجة «نجاح»، وإلا بقرار سلطان المكتوب. |

**لا تُكتب الحالة في مكانين.** الحالة الحية لمرحلة جارية تعيش في فرعها و worktree ها، لا في `main`؛ واللوحة تقرأها من هناك مباشرة.

## كيف تظهر الفروع غير المدمجة دون تعارض

- كل مرحلة يكتب حالتها **مالك واحد**: جلستها، في ملفها وحده. فلا تتعارض جلستان على ملف حالة.
- أداة المزامنة تقرأ كل سجل حيث يعيش، **قراءة فقط**: `main` المثبّت، وكل فرع محلي، وكل worktree (بما لم يُلتزم بعد)، وفرع التكامل. وتعرض مصدر كل حالة.
- ترتيب الأسبقية: «مدمجة ومتحققة» في `main` ← سجل فرع التكامل ← ملف الـworktree الحي ← رأس الفرع ← `main`.
- الفرع لا يستطيع أن يدّعي «مدمجة ومتحققة» أو «قيد الدمج»؛ هاتان يكتبهما المنسّق. والادعاء الخاطئ يظهر تنبيهًا في اللوحة وفي `plan:check`.
- مرحلتان على فرع واحد، أو مرحلة على فرعين، تنبيه يوقف الدمج.
- لا تُستنتج حالة من مرور الوقت ولا من صياغة تقرير. و`localStorage` لا يُستخدم لأي حالة.

## الحالات

| الحالة | المعنى | من يكتبها |
| --- | --- | --- |
| **مخططة** `planned` | لم تبدأ. وتظهر **«متاحة للبدء»** إن فُتحت موجتها وتحققت اعتمادياتها وفُتحت بواباتها، وإلا تُعرض أسباب انتظارها. | الخطة. |
| **جارية** `in_progress` | الجلسة تعمل في فرعها. | جلسة المرحلة. |
| **متعطلة** `blocked` | توقفت بسبب مكتوب وما يلزم لحله. | جلسة المرحلة، أو المنسّق عند فشل تكامل. |
| **جاهزة للدمج** `ready` | سُلّمت بتقرير وأدلة وفحوص المرحلة. **تسليم لا دمج.** | جلسة المرحلة. |
| **قيد الدمج** `integrating` | دُمجت في فرع التكامل، والبوابة لم تكتمل. | المنسّق. |
| **مدمجة ومتحققة** `verified` | في `main` بعد نجاح بوابة موجتها. **وحدها تُحسب منجزة.** | المنسّق. |

والموجة: **لم تُفتح** ← **مفتوحة** (بوسمها) ← **قيد الدمج** ← **مغلقة ومتحققة**، أو **متعطلة** بفشل بوابتها.

## التسميات

- الفرع: `tj/<ID>-<slug>` (مثل `tj/P3-export`). وإن بدأت الجلسة في worktree أنشأه التطبيق بفرع تلقائي فارغ، أنشأت المهارة فرع المرحلة فيه بالاسم الصحيح.
- مجلد العمل: `.claude/worktrees/tj-<ID>` (غير متتبَّع).
- فرع التكامل: `tj-int/<WAVE>`. وسم الأساس: `tj-<WAVE>/base`.
- رسائل الالتزام بالعربية: `P3: <ما أُنجز>`، وحفظ عمل غير مكتمل `P3: WIP — <ما أُنجز وما بقي>`، والأخير `P3: <النتيجة> — جاهزة للدمج في W3`، ودمج المنسّق `W3: دمج P3 — <العنوان>`، والتحقق `W3: تحقق الموجة — P3 · P4 · P5`.
- المستودع البعيد `origin`: مستودع GitHub خاص [`iSltanX/Tarjuman`](https://github.com/iSltanX/Tarjuman)، والدفع إليه بقواعد «الحفظ والدفع». لا نشر عام (جعل المستودع عامًا أو النشر في المتجر) دون طلب صريح من سلطان.

## الملكية والملفات المشتركة

- **كل مرحلة تملك:** ملفها في `docs/phases/`، ومجلد أدلتها `docs/evidence/<ID>/`، وما في `owns` من [`plan.json`](../../plan/plan.json) (يظهر في ملف المرحلة وفي [الموجات](waves.md)).
- **الملفات المشتركة** (جدول `shared` في `plan.json`): يملكها المنسّق، وبعضها تملكه P1 أو P2 في موجتها ثم يُجمَّد. لا تعدّلها جلسة مرحلة.
- **مسار الاستثناء:** إن احتاجت مرحلة تعديلًا في ملف مشترك لا تكتمل بدونه، تكتب طلبًا في `sharedRequests` (الملف، والتغيير، والسبب). فإن كان صغيرًا ومعزولًا جاز تطبيقه في التزام مستقل عنوانه `ملف مشترك: …` مع `applied: true`، ويراجعه المنسّق قبل الدمج. وإن كان تغيير عقد فالمرحلة **متعطلة** حتى يحسمه المنسّق على `main`.
- **عند التعارض في الدمج:** ملفات المرحلة وأدلتها لا تتعارض (مالك واحد). الملف المشترك الذي مسّه فرعان يُضمّ بترتيب الدمج ولا يُسقط أحد الجانبين. المولَّد يُعاد توليده بـ`npm run plan:render` بدل حل تعارضه يدويًا. وكتلة حالة مرحلة تؤخذ من فرعها ثم يكتب المنسّق حالة الدمج.

| الطبقة | الأمر | متى |
| --- | --- | --- |

## الحفظ والدفع

العمل يُحفظ في `origin` (مستودع GitHub الخاص) أولًا بأول، لا محليًا فقط ولا في نهاية المرحلة. تلتزم به كل جلسة مرحلة وكل منسّق.

- **التزام بعد كل مهمة:** بعد كل مهمة مكتملة ومتماسكة، شغّل فحوصها المناسبة (الطبقة السريعة للوحدة المعدّلة)، ثم التزم برسالة واضحة تصف ما أُنجز. لا تؤجّل حفظ العمل إلى نهاية المرحلة.
- **دفع بعد كل مهمة:** ادفع الالتزامات المكتملة فور التزامها: أول مرة `git push -u origin ‹BRANCH›`، وبعدها `git push`. جلسة المرحلة تدفع فرعها وحده.
- **قبل كل التزام:** راجع الفرق (`git status --short` ثم `git diff --cached --stat` بعد الإضافة)، وأضف ملفات مهمتك بأسمائها؛ لا `git add -A` ولا `git add .`. لا تُدخل تغييرات جلسة أخرى، ولا أسرارًا أو رموزًا أو روابط موقّعة، ولا ملفات مؤقتة أو سجلات، ولا ملفات تعريف المتصفحات (مجلد `Tarjuman-test` خارج المستودع، و`.tj-profiles/` متجاهَل).
- **لا التزام فارغ:** إن كانت التغييرات محفوظة بالفعل فلا التزام جديد؛ يكفي الدفع إن كان الفرع متقدمًا على نسخته البعيدة.
- **لا إعادة كتابة:** لا `push --force` ولا `--force-with-lease`، ولا `amend` أو `rebase` أو `reset` على التزام دُفع. ولا حذف فرع أو وسم بعيد إلا بموافقة سلطان، عدا فرع التكامل بعد تقديم `main` إليه (محتواه كله فيه).
- **عمل غير مكتمل:** يجوز حفظه على فرعه بالتزام `‹ID›: WIP — <ما أُنجز وما بقي>` ثم دفعه. هذا حفظ لا تسليم: لا يغيّر الحالة إلى «جاهزة للدمج».
- **التسليم:** الكود والاختبارات والأدلة وتقرير التسليم ملتزمة، ثم فرع المرحلة مدفوع. الدفع لا يعني الدمج.
- **إغلاق الموجة:** المنسّق وحده يدمج، بعد اجتياز بوابة الموجة، ثم يدفع `main` ووسم الأساس المعتمد للموجة التالية (بالاسم، لا `--tags`). لا تُدمج مرحلة تلقائيًا لمجرد اكتمالها أو دفعها.
- **الفشل:** إن فشل فحص أو تعذّر الدفع، فاذكر السبب ونص الخطأ كما هو، ولا تعلن نجاحًا غير حاصل. والالتزام غير المدفوع يُذكر في البلاغ «غير مدفوع» مع سببه.

## الاختبارات الحية وما يحتاجه سلطان

- قبل فتح أي متصفح أو التحكم بأي تطبيق، أرسل لسلطان **رسالة واحدة قصيرة** فيها: ما ستفتحه (Brave أو Chrome بملف تعريف اختبار منفصل)، وعدد الاختبارات، والمدة التقريبية بالدقائق، وما تحتاجه من يده إن وُجد (تحميل الإضافة غير المعبأة مرة واحدة، أو تسجيل دخول يوتيوب بنفسه)، وهل تحتاج «Enable computer use». ثم انتظر موافقته.
- لا تفترض أن «Enable computer use» مفعّل. إن احتجته فاطلب تفعيله (وضع Background) من Settings ← Desktop app ← Computer use، واذكر التطبيقات التي ستطلب إذنها، وانتظر تأكيده. وعند الانتهاء قل: «انتهيت، تقدر تطفّي Enable computer use».
- المتصفحات في computer use بدرجة «قراءة» فقط، فالتحكم يكون عبر CDP بملف تعريف اختبار: `--user-data-dir` خارج المستودع (مثل `~/Library/Application Support/Tarjuman-test/brave`) مع `--remote-debugging-port`. Chrome الرسمي يتجاهل `--load-extension` منذ الإصدار 137، ويرفض التحكم البعيد بملف التعريف الافتراضي منذ 136؛ فالبديل تحميل يدوي مرة واحدة في ملف الاختبار.
- لا تُدخل كلمات مرور ولا تنشئ حسابات. تسجيل الدخول إلى يوتيوب يقوم به سلطان بنفسه إن لزم.
- الأتمتة للاختبار فقط وبوتيرة بشرية. إن ظهر تحدي «لست روبوتًا» فتوقف وسجّل، ولا تتحايل.
- لا تجعل سلطان ينفّذ خطوات الاختبار بيده بدلك؛ يده تُطلب لما لا يمكن غيره فقط.
- الأدلة في `docs/evidence/<ID>/`: جدول النتائج، ولقطات، وسجلات منقّاة من أي رابط أو رمز.

## دور: جلسة مرحلة

جلسة Claude Code مستقلة يفتحها سلطان وينسخ فيها `/tj-phase ‹ID›` أو البرومبت الكامل. تعمل في worktree خاص بالمرحلة على فرعها `‹BRANCH›`، وتنفّذ نطاق ‹ID› وحده، وتفحصه، وتسلّمه، وتتوقف.

1. **تحقّق قبل أي عمل** — كل شرط يُقاس بأمر تشغّله أنت، وسقوط واحد يوقف الجلسة بطباعة ما سقط وما يلزم:
   - `command node tools/plan/plan.mjs brief ‹ID›` يطبع بطاقة المرحلة دون خطأ.
   - المرحلة **متاحة للبدء** (الموجة مفتوحة بوسم `tj-‹WAVE›/base`، والاعتماديات «مدمجة ومتحققة»، والبوابات مفتوحة)، أو **جارية/متعطلة** على فرعها فهو استئناف. وإن كانت «جاهزة للدمج» أو بعدها فلا تعمل إلا بطلب صريح من سلطان لإصلاح محدد.
2. **مكان العمل** — لا تعمل على `main` أبدًا:
   - **استئناف:** إن وُجد worktree المرحلة فادخله بأداة `EnterWorktree` (بالمعامل `path`). وإن وُجد فرعها بلا worktree: `git worktree add .claude/worktrees/tj-‹ID› ‹BRANCH›` ثم ادخله.
   - **بدء من النسخة الرئيسية:** `git worktree add .claude/worktrees/tj-‹ID› -b ‹BRANCH› main` ثم `EnterWorktree` (`path`).
   - **بدء من worktree أنشأه التطبيق:** إن كان فرعه تلقائيًا بلا تغييرات ولا التزامات فوق `main` (`git status --porcelain` فارغ و`git rev-list --count main..HEAD` صفر) فـ`git switch -c ‹BRANCH› main`. وإلا توقّف.
   - ثم تحقّق: `git rev-parse --abbrev-ref HEAD` يساوي `‹BRANCH›`، و`git merge-base --is-ancestor tj-‹WAVE›/base HEAD` ناجح.
3. **سجّل البدء:** `command node tools/plan/plan.mjs set ‹ID› status=in_progress branch=‹BRANCH› resume="…"` ثم التزام `‹ID›: بدء المرحلة`، ثم `git push -u origin ‹BRANCH›`.
4. **الاختبار الحي:** إن احتاجت المرحلة متصفحًا أو تطبيقًا على الجهاز، فأرسل رسالة «الاختبارات الحية» قبل فتح أي شيء، وانتظر الموافقة.
5. **التنفيذ** داخل نطاق ملف المرحلة وملكيتها وحدها، مهمةً مهمة: بعد كل مهمة مكتملة ومتماسكة فحوص الطبقة السريعة للوحدة المعدّلة، ثم مراجعة الفرق، ثم التزام بملفاتها بأسمائها برسالة عربية تبدأ بـ`‹ID›: ` تصف ما أُنجز، ثم `git push` (قسم «الحفظ والدفع»). لا تؤجّل الحفظ إلى نهاية المرحلة. وحدّث `resume` عند كل نقطة توقف طبيعية. وكيل فرعي واحد صغير لمهمة معزولة فقط إن لزم، وتقريره بالعربية.
6. **إن تعطّلت:** `set ‹ID› status=blocked blocker="السبب وما يلزم لحله"`، والتزام ودفع، ثم اشرح لسلطان بسطرين وتوقّف.
7. **التحقق مرة قرب التسليم:** أوامر فحوص المرحلة، ثم إثبات كل معيار قبول بدليل في `docs/evidence/‹ID›/`، وتسجيل النتائج في كتلة `tj-status` (`checks` و`acceptance` و`evidence`، و`outcome` في مرحلة البوابة).
8. **التسليم:** `set ‹ID› status=ready commit=<آخر التزام عمل> resume="جاهزة للدمج في ‹WAVE›"`، ثم سجل التنفيذ وتقرير التسليم بصيغته في ملف المرحلة، ثم `command node tools/plan/plan.mjs check --phase ‹ID›`، ثم التزام أخير `‹ID›: <النتيجة> — جاهزة للدمج في ‹WAVE›` (الكود والاختبارات والأدلة وتقرير التسليم)، ثم `git push` وتحقّق أن `git status -sb` لا يُظهر الفرع متقدمًا على `origin/‹BRANCH›`. لا دمج. اطبع التقرير بالعربية مع نتيجة الدفع وتوقّف.

**ممنوع في هذا الدور:** الدمج في `main` أو العمل عليه · لمس فرع مرحلة أخرى أو ملفها · تعديل ملف مشترك خارج مسار الاستثناء · تعديل `plan/` أو `docs/delivery/` أو `docs/waves/` أو اللوحة أو المهارات أو الوسوم · إعادة الفحص الكامل بعد كل تعديل صغير · بدء مرحلة أخرى · دفع غير فرع المرحلة، أو `push --force`، أو إعادة كتابة تاريخ مدفوع، أو النشر العام · اعتبار خضرة الفرع وحده نجاحًا للتكامل · تحويل النطاق بنفسك عند الفشل.

## دور: منسّق الموجة

جلسة في **النسخة الرئيسية** على `main` بلا worktree، يفتحها سلطان بعد تسليم مراحل الموجة ‹WAVE› وينسخ فيها `/tj-merge ‹WAVE›`. تكتشف الفروع بنفسها؛ لا يكتب سلطان اسم فرع ولا أمر Git.

1. **الشروط:** الجلسة في النسخة الرئيسية (`git rev-parse --git-dir` يساوي `git rev-parse --git-common-dir`)، وعلى `main`، والشجرة نظيفة، و`main` لا ينقصه شيء من `origin/main` بعد `git fetch origin` (`git rev-list --count main..origin/main` صفر)، والوسم `tj-‹WAVE›/base` موجود، ولا وسم للموجة التالية. وإن وُجد فرع التكامل `tj-int/‹WAVE›` فهو استئناف لدمج سابق: تابع من آخر خطوة مسجلة في سجل الموجة.
2. **الاكتشاف:** `command node tools/plan/plan.mjs discover ‹WAVE›` يطبع لكل مرحلة فرعها وحالتها وآخر التزام وتقريرها وفحص ملكيتها. يلزم أن تكون كل مراحل الموجة «جاهزة للدمج» بتقرير تسليم، وألا يمس فرع ملفًا خارج ملكيته دون طلب مسجّل. وإلا توقّف واطبع ما ينقص ومن يكمله. وفرع كل مرحلة مدفوع بتمامه (`git rev-list --count origin/<الفرع>..<الفرع>` صفر)؛ وإن لم يكن فادفعه كما هو بـ`git push origin <الفرع>` وسجّل ذلك في سجل الموجة.
3. **فرع التكامل:** `git switch -c tj-int/‹WAVE› main`، ثم `command node tools/plan/plan.mjs wave-set ‹WAVE› status=merging integrationBranch=tj-int/‹WAVE›`.
4. **الدمج بالترتيب:** لكل مرحلة بترتيب الموجة: `git merge --no-ff <الفرع> -m "‹WAVE›: دمج <ID> — <العنوان>"`، ثم `set <ID> status=integrating mergeCommit=<التزام الدمج>`، ثم `npm run check:quick` إن وُجد. التعارض يُحلّ بقواعد «الملكية والملفات المشتركة» لا باختيار نسخة، ويُسجَّل حلّه في سجل الموجة.
5. **لا تغيير سقط:** `command node tools/plan/plan.mjs verify-merge ‹WAVE›` — كل ملف غيّره فرع مرحلة يطابق رأس التكامل، أو يُنسب فرقه إلى مرحلة دُمجت بعده أو إلى حل تعارض مسجّل.
6. **بوابة الموجة** على الشجرة النظيفة: أوامر البوابة في `plan.json`، ثم الدخان الحي إن وُجد (برسالة «الاختبارات الحية» نفسها). الأحمر بسبب خلل تكامل يُصلَح بالتزام صغير على فرع التكامل ويُعاد الساقط وحده ثم البوابة مرة. وإن كان الخلل داخل مرحلة فـ`set <ID> status=blocked blocker="…"` و`wave-set ‹WAVE› status=blocked`، والتزام، و`git push -u origin tj-int/‹WAVE›` ليُحفظ ما دُمج، وتوقّف: تعود المرحلة إلى جلستها.
7. **التثبيت:** لكل مرحلة `set <ID> status=verified`، و`wave-set ‹WAVE› status=verified gate=pass`، ثم `npm run plan:render` و`npm run plan:check`، وسجل الموجة وتقريرها، والتزام واحد `‹WAVE›: تحقق الموجة — <المراحل>`.
8. **التقدّم والدفع:** `git switch main && git merge --ff-only tj-int/‹WAVE›`، ثم `git push origin main`، ثم `git branch -d tj-int/‹WAVE›` (و`git push origin --delete tj-int/‹WAVE›` إن كان قد دُفع).
9. **البوابة والفتح:** إن كانت الموجة تحسم بوابة (W1 تحسم G1): نتيجة «نجاح» تفتحها. وغير ذلك: اعرض تقرير المرحلة وأسبابها وبدائلها وخيارات البوابة من `plan.json`، واطلب قرار سلطان، ولا تتابع حتى يكتبه. سجّل القرار بنصه: `wave-set ‹WAVE› decision="…" decisionState=open|closed`، والتزم، و`git push origin main`. وإن غيّر القرار النطاق، فاعرض تعديل `plan.json` و`product-spec.md` نصًا واطلب الموافقة قبل التزامه. ثم إن كانت البوابة مفتوحة أو لا بوابة: `git tag tj-‹NEXT›/base` ثم `git push origin refs/tags/tj-‹NEXT›/base`.
10. **اللقطة والتنظيف:** `npm run plan:sync`. ثم اعرض worktrees المراحل المدمجة وفروعها، واحذفها **فقط بموافقة سلطان**: `git worktree remove` للنظيف منها، و`git branch -d` للمدمج، و`git push origin --delete <الفرع>` لنسخته البعيدة.
11. **البلاغ:** تقرير الموجة بصيغته بالعربية مع ما دُفع إلى `origin` (`main` عند بصمته والوسم) أو سبب تعذّره، والموجة التالية ومراحلها المتاحة وأوامرها ونماذجها. توقّف.

**ممنوع:** دفع `main` أو وسم قبل نجاح البوابة · النشر العام · `push --force` وإعادة كتابة التاريخ و`--no-verify` · تقديم `main` قبل نجاح البوابة · وضع وسم على التزام لم يجتزها · دمج فرع بلا تقرير تسليم · تنفيذ عمل مرحلة بدل جلستها (عدا إصلاح تكامل صغير مسجّل) · فتح موجة تنتظر قرار بوابة دون قرار سلطان المكتوب.

## ملاحظات البيئة

- في جلسات Claude Code على هذا الجهاز قد يكون `node` و`npm` دالتين معطوبتين في الصدفة (`_load_nvm`). استعمل `command node …` و`command npm run …` لتجاوزهما.
- أدوات الخطة بلا اعتماديات خارجية، وتعمل بـNode 20 فأحدث.
- القراءة من worktrees الجلسات الأخرى تتم مع `GIT_OPTIONAL_LOCKS=0` فلا تأخذ أقفال فهارسها.
- الدفع بـHTTPS عبر بيانات `gh` المسجّلة (`gh auth status`). إن طلب الدفع اعتمادًا أو رُفض فذلك «تعذّر الدفع»: يُذكر سببه، ولا تُدخل الجلسة رمزًا ولا كلمة مرور.
